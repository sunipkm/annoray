Units and quantities#

In annoray a physical unit is part of the data, not an attribute beside it. Every DataArray carries a Unit (or none), single values with a unit are Quantity objects, and every operation checks that the units of its operands fit together. A CF units attribute is decoded into a unit when a file is opened and written back when it is saved.

import numpy as np
import annoray as ar

Writing units#

Units are written in the UDUNITS-2 grammar that the CF conventions use, so every units attribute of a CF file parses as it is. The same unit has several spellings:

same = ["m/s", "m s-1", "m.s-1", "m s^-1", "meters per second", "m.s**-1"]
print({ar.Unit(s) == ar.Unit("m/s") for s in same})

{True}

A string that does not parse is an error when the unit is made, not later:

try:
    ar.Unit("meters per fortnite")
except ar.UnitError as e:
    print("UnitError:", e)

UnitError: unknown unit "fortnite"

Units on data#

speed = ar.DataArray([4.0, 12.5, 30.0], dims="t", units="km/h")
print(speed.units, "→", speed.to("m/s").values)

km/h → [1.11111111 3.47222222 8.33333333]

to converts to any unit of the same dimension, exactly where the conversion factor is a rational number (inches to centimetres is 127/50, not a rounded float); conversions that involve π, such as degrees to radians, are as exact as a double allows. float32 data stays float32.

A file’s CF units attribute becomes the unit of the variable it belongs to, and to_netcdf writes the unit back as the attribute. Units are therefore never stale: there is no attribute that can disagree with the data after a conversion.

A units attribute that does not parse (a typo, or a spelling outside UDUNITS-2 and CF, such as "counts per detector pixel"), in a file or given to a constructor, is kept as a plain attribute, with a warning naming the reason. The variable then has no unit: conversions and unit checks refuse it instead of guessing, and the attribute is written back unchanged. open_dataset(decode_units=False) keeps every units attribute as text, without warnings, as xarray does.

import warnings

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    odd = ar.DataArray([1.0, 2.0], dims="x", attrs={"units": "counts per detector pixel"})
print(odd.units, odd.attrs["units"])
print(caught[0].message)

None counts per detector pixel
units "counts per detector pixel" kept as an attribute: unknown unit "detector"

Quantities#

d = ar.Quantity(2.5, "km")
t = ar.Quantity(30, "min")
v = d / t
print(v, "=", v.to("m/s"))
print(ar.Quantity(1, "km") == ar.Quantity(1000, "m"), ar.Quantity(1, "km") > ar.Quantity(900, "m"))

0.08333333333333333 km min-1 = 1.3888888888888888 m/s
True True

A quantity is also made by multiplying a number by a unit (2.5 * ar.Unit("km")), and is accepted wherever a value with a unit is expected: as an operand of a data array, as a label in sel, as the value of put, where and fillna.

A quantity’s unit is interned: each spelling is parsed once and kept in a process-wide table, so quantities are cheap to make and copy. The table is capped (65,536 units by default, set_intern_cap()); past the cap, a quantity in a new unit is a UnitError.

Complex quantities#

A quantity’s magnitude is a float or a complex. A complex quantity follows the rules of complex data: conversion scales both parts (a unit with an offset, such as °C, does not convert), real and complex operands give a complex result, and there is no order (== and != only). .real, .imag and abs() are real quantities in the same unit, and .item() of complex data with a unit is a complex quantity.

v = ar.Quantity(3 + 4j, "V")
i = ar.Quantity(0.5j, "A")
print(v / i)  # an impedance
print(v.real, v.imag, abs(v), v.to("mV"))
z = ar.DataArray([1 + 2j, 3 - 1j], dims="x", units="V")
print(repr(z.sum().item()))
try:
    v < v.conjugate()
except TypeError as e:
    print("TypeError:", e)

(8-6j) V A-1
3.0 V 4.0 V 5.0 V (3000+4000j) mV
Quantity((4+1j), "V")
TypeError: complex quantities have no order: compare .real, .imag or abs()

Arithmetic rules#

annoray refuses operations whose result would depend on an unstated assumption about units.

Dimensions must match for +, - and comparisons:

try:
    speed + ar.Quantity(1.0, "m")
except ar.UnitError as e:
    print("UnitError:", e)

UnitError: incompatible units: km/h and m

Scales must match too. Adding kilometres to metres is not guessed at: the result’s unit would have to be chosen silently. One operand is converted first:

a = ar.Quantity(1.0, "km")
b = ar.Quantity(250.0, "m")
try:
    a + b
except ar.UnitError as e:
    print("UnitError:", e)
print(a + b.to("km"))

UnitError: units km and m differ in scale; convert one first
1.25 km

Comparisons convert compatible units (1 km > 900 m above); they only decide, they produce no unit.

*, / and powers combine units: km / min above, m s-1 * s is m. Integer powers and exact roots of dimensioned data work ((m2) ** 0.5 is m); other powers need dimensionless data.

Temperatures and other offset units. The difference of two absolute temperatures is a temperature step, in kelvin-sized degrees; their sum has no meaning:

print(ar.Quantity(20, "degC") - ar.Quantity(15, "degC"))
try:
    ar.Quantity(20, "degC") + ar.Quantity(15, "degC")
except ar.UnitError as e:
    print("UnitError:", e)

5.0 K
UnitError: adding two absolute temperatures is not defined for degC

Products of offset units (degC * m) are errors: convert to an absolute scale (K) first. Sums over a dimension (sum) refuse °C; mean, min and max keep it, and std is a step in K.

Logarithmic units (dB, B) convert only between the same reference.

Functions. Transcendental functions (np.exp, np.log) need dimensionless input; np.sin, np.cos and np.tan take angles (converted to radians) or plain numbers; inverse trigonometric functions of data with a unit return radians. NumPy ufuncs without a unit rule refuse data with a unit instead of dropping it.

Plain numbers beside units#

A number without a unit next to data with one is accepted only where its meaning does not depend on the unit: 0 (for ratio-scale and logarithmic units) and NaN. Any other value is given as a quantity, so that a threshold cannot silently be in the wrong unit:

temp = ar.DataArray([281.2, 283.9, 290.5], dims="x", units="K")
print(temp.where(temp > ar.Quantity(10, "degC")).values)
try:
    temp > 10
except ar.UnitError as e:
    print("UnitError:", e)

[  nan 283.9 290.5]
UnitError: incompatible units: K and 1

The same rule applies to where, fillna, clip, isin, put and query.

Time#

Time units with an epoch (days since 2000-01-01, hours since 1970-01-01 00:00) are decoded into dates in the variable’s CF calendar (all CF calendars are supported). A time unit without an epoch (days, hours) is a duration and stays a quantity; to() converts it like any other unit. months and years are refused as epochs, as cftime refuses them: their length varies.

Dimension annotations#

annoray.dims names dimensions as classes. They make checked quantities, recognise them, and annotate functions; annoray.dims.checked() enforces the annotations at every call:

from annoray.dims import Length, Time, Velocity, Dim, checked
from annoray import Quantity

class Jerk(Dim, dimension=Length / Time**3):
    """Rate of change of acceleration."""

@checked
def mean_speed(d: Quantity[Length], t: Quantity[Time]) -> Quantity[Velocity]:
    return d / t

print(mean_speed(Length(42.195, "km"), Time(2.1, "h")).to("km/h"))
print(isinstance(ar.Quantity(3, "m s-3"), Jerk))
try:
    mean_speed(Time(1, "h"), Time(2.1, "h"))
except ar.UnitError as e:
    print("UnitError:", e)

20.09285714285714 km/h
True
UnitError: mean_speed(): argument 'd': expected Length [m], got Time

In Rust the same names are types, and the check happens at compile time:

use annoray::dims::{Length, Time, Velocity};
use annoray::Quantity;

let d = Quantity::<Length>::new(2.5, "km")?;
let t = Quantity::<Time>::new(30.0, "min")?;
let v: Quantity<Velocity> = (&d / &t)?; // any other dimension is a type error

Other unit libraries#

  • astropy (annoray[astropy]): to_astropy() on units, quantities and arrays, and annoray.from_astropy(). Units correspond through their SI-plus-radian decomposition, and keep their names where both libraries define a name the same way.

  • xarray and pint-xarray: to_xarray() writes the unit as the units attribute, as pint-xarray and cf-xarray expect.

  • Rust: the uom and whippyunits features convert to and from those crates’ compile-time quantities.
