# annoray — Plan

A units-aware port of Python's xarray in Rust. It reads and writes netCDF-3, netCDF-4 and HDF5.
The data model copies ndarray's owned/view split: `Dataset`, `DatasetView`, `DatasetViewMut`.

## Decisions

| Topic | Decision |
|---|---|
| Name | **annoray** (annotated arrays): the Rust crate `annoray` (a facade over the `annoray-*` crates: core, units, io, io-c, cf, hdf5, netcdf3, netcdf4, macros, published first since `annoray` depends on them) and the Python package `annoray` (crate `annoray-python`, module `annoray._annoray`). The project began as `xarray-rs` (crates `xr-*`) and the Python package as `rarray` |
| View naming | ndarray style: `DatasetView<'a>`, `DatasetViewMut<'a>`, `DataArrayView<'a>`, … |
| Units | Runtime port of **whippyunits'** model: prime-factorized scales, data kept in the unit it is declared in, exact unit equality, affine units, angle as its own dimension |
| Time | **chrono**: `NaiveDateTime` for real-world calendars, `TimeDelta` for durations. Non-Gregorian CF calendars use our own `CfDate` type, which converts to and from chrono where possible |
| Typed-unit interop | `uom` and `whippyunits` behind feature flags of the same names, both going through one `StaticUnit` trait |
| HDF5 / netCDF-4 | Our own pure-Rust reader and writer in the long run |
| Bootstrapping | Start with C bindings (`netcdf` and `hdf5-metno` crates) behind the `c-backend` feature. Keep them afterwards as test oracles |
| I/O milestones | Each format ships read and write together, with a round-trip test |
| MSRV | Rust 1.97, edition 2024 (raised from 1.85 during M8) |
| Errors | No `unwrap`, `expect` or `panic!` in library code. Every failure is propagated as a `Result`, and lints enforce this (§2a) |

## 1. Workspace layout

```
annoray/
├── crates/
│   ├── annoray-units       # Unit, Scale, Dimension, parser (UDUNITS/CF + UCUM), conversion, CF time,
│   │                       #   typed Quantity<D>; usable on its own (depends on chrono and typenum only)
│   ├── annoray-hdf5        # pure Rust HDF5 (superblock, object headers, B-trees, heaps, chunking,
│   │                       #   filters, writer); usable on its own: its own Array, Error, Compression
│   └── annoray-macros      # proc macros: isel!/sel! with Python-style slices (syn + quote)
├── annoray/                # the library: data model at the root, plus modules
│   │                       #   cf (CF encode/decode), io (Backend, RawDataset, open_dataset/to_netcdf),
│   │                       #   io::netcdf3, io::netcdf4 (on annoray-hdf5), io::netcdf_c [feature netcdf-c]
├── annoray-python/         # Python bindings (not published to crates.io)
└── fixtures/               # Python xarray/netCDF4/h5py scripts → golden files; test-only
```

The C backend and the pure-Rust backends implement the same `annoray::io::Backend` trait. That lets the
whole test suite run against both, and lets us diff their outputs.

**Why only three sibling crates** (2026-10): the data model, CF layer, I/O model and the netCDF
backends were separate crates (`annoray-core`, `-cf`, `-io`, `-io-c`, `-netcdf3`, `-netcdf4`), but
none was usable without the core, so they were merged into `annoray` as modules (the C backend is the
`netcdf-c` feature). What stays separate is what is useful elsewhere: units, the HDF5 reader/writer,
and the proc-macro crate (which must be its own crate). `annoray-hdf5` no longer depends on annoray's
types: it has its own `Array`/`ValueType`, `Error`, `Compression` (re-exported by annoray), a `Source`
trait for streaming writes, and `set_batch_bytes` (which `annoray::set_stream_bytes` also sets).
Section names below that mention the old crates refer to these modules.

## 2. Core data model (`annoray-core`)

A single generic base type, with the storage kind (owned, view, mutable view) chosen through a GAT:

```rust
pub trait Repr { type Arr<T: Element>; type Attrs; }

pub struct Owned;
pub struct View<'a>(PhantomData<&'a ()>);
pub struct ViewMut<'a>(PhantomData<&'a mut ()>);

impl Repr for Owned           { type Arr<T: Element> = ArrayD<T>;              type Attrs = Attrs; }
impl<'a> Repr for View<'a>    { type Arr<T: Element> = ArrayViewD<'a, T>;      type Attrs = &'a Attrs; }
impl<'a> Repr for ViewMut<'a> { type Arr<T: Element> = ArrayViewMutD<'a, T>;   type Attrs = &'a Attrs; }

pub enum TypedArray<S: Repr> {           // dispatch code generated by a macro
    F32(S::Arr<f32>), F64(S::Arr<f64>),
    I8(S::Arr<i8>),   I16(S::Arr<i16>), I32(S::Arr<i32>), I64(S::Arr<i64>),
    U8(S::Arr<u8>),   U16(S::Arr<u16>), U32(S::Arr<u32>), U64(S::Arr<u64>),
    Bool(S::Arr<bool>), Str(S::Arr<String>),
    DateTime(S::Arr<chrono::NaiveDateTime>),   // standard / gregorian / proleptic_gregorian
    CfDate(S::Arr<CfDate>),                    // noleap, all_leap, 360_day, julian, pre-1582 standard
    TimeDelta(S::Arr<chrono::TimeDelta>),      // only when explicitly requested; see §3
}

pub struct VariableBase<S: Repr> {
    data:  Data<S>,              // Loaded(TypedArray<S>) | Lazy(Arc<dyn BackendArray>, Selection)
    dims:  DimNames,             // SmallVec<[Name; 4]>
    unit:  Option<Unit>,         // small value type, copied into views
    attrs: S::Attrs,
}

pub struct DatasetBase<S: Repr> {
    vars:    IndexMap<Name, VariableBase<S>>,
    coords:  IndexSet<Name>,
    indexes: Indexes,            // Arc<dyn Index>; cheap to clone into views
    attrs:   S::Attrs,
}

pub type Dataset            = DatasetBase<Owned>;
pub type DatasetView<'a>    = DatasetBase<View<'a>>;
pub type DatasetViewMut<'a> = DatasetBase<ViewMut<'a>>;
// DataArray / DataArrayView / DataArrayViewMut and Variable* follow the same pattern
```

Rules:
- `view()`, `view_mut()` and `to_owned()` behave as in ndarray. `isel` and `sel` keep the mutability of the value they are called on.
- A `ViewMut` can change **data only**. Coordinates, indexes, dims and attrs are read-only through it.
  Each variable owns a separate buffer, so splitting `&mut` borrows across variables is sound.
- Lazy variables can be viewed but not mutably viewed. Call `.load()` first.
- Dimensions are named and dynamic. Broadcasting and alignment work by name, and ndarray axis order is an internal detail.
- Typed access: `da.data::<f64>()? -> ArrayViewD<f64>`. With units: `da.quantity::<f64>()? -> (ArrayViewD<f64>, Unit)`.

## 2a. Error handling (applies to every crate)

**Rule:** library code never panics on any input, whether it comes from users, files or the network.
Every failure is returned as a `Result`.

**Enforced through workspace lints** (in the root `Cargo.toml`, inherited by every crate with `[lints] workspace = true`):

```toml
[workspace.lints.clippy]
unwrap_used        = "deny"
expect_used        = "deny"
panic              = "deny"
todo               = "deny"
unimplemented      = "deny"
unreachable        = "deny"   # use an Error::Internal variant instead
indexing_slicing   = "deny"   # always .get(..)/.get_mut(..) → ok_or(..)? ; no local #[allow] escapes
arithmetic_side_effects = "warn"  # file-derived sizes need checked_* arithmetic
unwrap_in_result   = "deny"
missing_errors_doc = "warn"
```

`clippy.toml` has `allow-unwrap-in-tests = true` and `allow-expect-in-tests = true`. Tests, examples
and benches may unwrap, but library code may not.

**Error types:**
- Each crate has its own `thiserror` enum: `UnitError`, `CoreError`, `CfError`, `Nc3Error`,
  `Hdf5Error`, …
- The facade crate's `annoray::Error` wraps them all with `#[from]`, so `?` works everywhere.
- Errors carry context (variable name, dimension, file offset, HDF5 object address) so failures in
  large files can be located. A small `ResultExt::context()` helper adds it.
- Enums are `#[non_exhaustive]`. No `Box<dyn Error>` in public APIs.

**Fallible operators.** Unit or dimension mismatches are runtime errors, so the arithmetic operators return `Result`:

```rust
impl Add<&DataArray> for &DataArray { type Output = Result<DataArray>; … }
impl Add<&DataArray> for Result<DataArray> { type Output = Result<DataArray>; … } // allowed by the orphan rules
let c = (&a + &b * &k)?;         // chains, single `?` at the end
let c = a.try_add(&b)?;          // named methods too
```

**Untrusted file input:**
- Every size, offset and count read from a file goes through `checked_mul` / `checked_add` /
  `usize::try_from`.
- Buffers are allocated with `try_reserve`, after checking the requested size against the file
  length and `OpenOptions::max_alloc`.
- A corrupt file must give `Err`, never a panic, an abort, or a huge allocation. Fuzzing (§7) checks this.

**Indexing:** always `.get()` / `.get_mut()`, never `[]`. This applies to slices, `Vec`, `IndexMap`,
and ndarray (`arr.get(ix)`, `slice` only after shape validation goes through a checked helper). Code may not
locally `#[allow(clippy::indexing_slicing)]`, even where a shape check came first. Shared helpers
(`get_or_err(&slice, i, || Error::…)`) keep this readable.

**Third-party panics:** ndarray panics on shape mismatches in some APIs, and chrono in some
constructors. We use the non-panicking variants (`from_shape_vec`, `checked_add_signed`,
`NaiveDate::from_ymd_opt`, …) and check shapes before calling anything that can panic.

## 3. Units (`annoray-units`), modelled on whippyunits

whippyunits checks units at compile time. Units in netCDF files are only known once the file is read,
so we keep its **algebra** and evaluate it at runtime.

### Representation

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash)]
pub struct Dimension {          // integer exponents of the base dimensions
    pub mass: i8, pub length: i8, pub time: i8, pub current: i8,
    pub temperature: i8, pub amount: i8, pub luminosity: i8,
    pub angle: i8,              // first-class, as in whippyunits; erasable
}

#[derive(Clone, Copy, PartialEq, Eq, Hash)]
pub struct Scale {              // value_SI = value * 2^p2 * 3^p3 * 5^p5 * π^pπ * residual
    pub p2: i16, pub p3: i16, pub p5: i16, pub ppi: i16,
    pub residual: Ratio<i64>,   // reduced; 1 for nearly all units (inch: 127/50 after factoring)
}

pub struct Unit {
    pub dim: Dimension,
    pub scale: Scale,
    pub kind: UnitKind,         // Linear | Affine { offset: Ratio<i64> } (degC, degF) | Epoch(TimeUnit)
    pub label: Option<Arc<str>>,// original string, written back unchanged on save
}
```

Why factor scales into primes, as whippyunits does:
- km, ms, hours (2⁴·3²·5²), minutes, degrees (π·2⁻²·3⁻²·5⁻¹) and all SI prefixes are exact. Rescaling
  between them adds and subtracts exponents, so no floating-point error builds up and unit equality is
  exact (`==`, `Hash`) with no tolerance.
- Rescaling integer data (`i16` in mm to `i32` in µm) can use exact rational arithmetic, matching
  whippyunits' guarantee that integer storage only does integer math.

### Semantics (following whippyunits)

| Op | Rule |
|---|---|
| Storage | Values stay in the unit they were declared in. A `mm` variable is never normalized to `m` behind your back |
| `a + b`, `a - b`, comparisons | Dimensions must match. **Different scales are an error by default**; call `b.rescale_to(a.unit())` explicitly. Setting `UnitPolicy::AutoRescale` instead converts to the left-hand unit |
| `a * b`, `a / b` | Dimensions add or subtract, and scales multiply into the result (`m / ms` keeps a 10³ factor). `simplify()` is optional |
| `powi`, `sqrt` | Exponents are multiplied, or halved. `sqrt` needs even exponents |
| Reductions | `sum`, `mean`, `min`, `max` and `std` keep the unit. `var` squares it. `count` is dimensionless |
| Affine | `degC - degC` gives a kelvin-scale delta. `degC + delta` gives `degC`. `degC + degC` is an error. Products of affine units are an error unless converted first |
| Angle | `.erase_angle()` (whippyunits' `.into()`) folds angle into dimensionless, applying the scale for degrees. `sin`/`cos` erase angle automatically |
| Epoch | `days since 1970-01-01` is not a scale. It is `UnitKind::Epoch { step: Unit, epoch: CfDate, calendar }`, and CF decoding turns it into datetimes (see Time below) |

Planned, not required for v1:
- **Brands.** whippyunits brands quantities to separate contexts such as coordinate frames. An optional
  `brand: Option<Name>` could do the same here, for example keeping `heights_above_geoid` from mixing
  with `heights_above_ellipsoid`.

### Parsing and formatting
- **UDUNITS-2 / CF grammar,** which is what files contain: `m s-1`, `m/s`, `kg m-2 s-1`, `W m**-2`, `hPa`,
  `degC`, `degrees_north`, `1`, `percent`, `psu`, plus `since` clauses.
- **UCUM grammar,** which whippyunits uses: `kg.m2/s2`.
- `Display` uses the stored label when there is one, and otherwise a canonical CF form.
- **Unit tables:** generated from the UDUNITS XML by `tools/gen_unit_table.py` into a committed
  `table.rs` (not at build time, so builds need no network or XML). Every one of the ~300 UDUNITS
  definitions resolves, and every canonical unit in CF standard-name table v95 parses (tests).

### Implementation notes (M1, as built)
- **Negative scales are allowed:** UDUNITS defines `degree_west = -1 degree_east`. The sign lives
  in `Scale`'s residual. Zero factors are rejected.
- **Prefix lookup is permissive, like UDUNITS:** a prefix symbol may precede a unit name (`dbar`,
  `mbar`). Exact matches always win (`min` is minutes, not milli-inches).
- **Offsets inside products are dropped,** as UDUNITS does: `kg degree_C m-2` means kg K m-2. The
  public `Unit::mul` on an affine unit is still an error. Call `.delta()` first.
- **Logarithmic units** (`B`, `dB`, `dBZ`, `lg(re 1 mW)`) are `UnitKind::Log`. Prefixes scale them,
  and they convert only between the same reference. No other arithmetic is allowed.
- **Allowed epoch steps:** whole seconds (s … weeks) or exact divisors of a second (ms, µs, ns).
  UDUNITS' `month` and `year` are fractional-second astronomical lengths, so `months since` is
  rejected, as cftime does.
- **Time semantics match cftime 1.6:** `standard`/`julian` have no year 0, while
  `proleptic_gregorian` and the idealized calendars do. Float offsets round to the nearest µs (ties
  to even). Reference-date time zones are applied. 5,040 cases checked against cftime.
- **Checked arithmetic:** a crate-private `Ck` integer wrapper propagates overflow as `None`, and
  `clippy.toml` allow-lists it (`arithmetic-side-effects-allowed = ["ck::Ck"]`; clippy matches the
  crate-relative path).

### Time (chrono)

chrono only knows the proleptic Gregorian calendar, while CF files also use other calendars. So time is split as follows:

| CF calendar | Decoded element | Notes |
|---|---|---|
| `proleptic_gregorian` | `chrono::NaiveDateTime` | Direct |
| `standard` / `gregorian` | `NaiveDateTime` if every value is on or after 1582-10-15, otherwise `CfDate` | Before 1582 the `standard` calendar is Julian, and chrono would silently get it wrong |
| `noleap`/`365_day`, `all_leap`/`366_day`, `360_day`, `julian` | `CfDate` | `CfDate { calendar, y, m, d, h, mi, s, ns }` with calendar-aware arithmetic |

- **Converting `CfDate` to chrono:** `TryFrom<CfDate> for NaiveDateTime` fails on dates that don't exist
  in chrono's calendar (360_day Feb 30). For bulk conversion, `cf.to_chrono_lossy(Policy::{Error, ClampToMonthEnd})`.
- **Decoding numbers to dates:** `epoch + n * step`, computed with `chrono::TimeDelta` (or `CfDate`
  arithmetic). Integer offsets use exact integer arithmetic. Float offsets are rounded to the
  precision of the step unit, as cftime does, so `0.1 days` doesn't come out as `2:23:59.999`.
- **Encoding dates to numbers:** keep the original `units` and `calendar` attributes, so data written
  back to a file stays bit-for-bit identical.
- **Indexes:** `sel` takes `NaiveDateTime`, `NaiveDate`, `&str` (parsed as ISO 8601) or `CfDate`. The
  `resample`/`groupby` time bins (later milestones) are built on `chrono::Datelike`.
- **Durations:** variables with time units and no `since` (e.g. `hours`) stay **quantities** with a time
  dimension, so units still apply. `da.to_timedelta()` converts them to `TimeDelta` on request.
  Subtracting two datetimes gives `TimeDelta`. Converting a `TimeDelta` array back to a quantity gives `s`.

### Typed quantities (`Quantity<D>`, `dims`, `dimension!`)

Quantities in Rust follow physics. Dimensions are the exponents of the eight base quantities
(the seven SI ones plus angle), and users compose derived dimensions from them; there are no
new base dimensions.
- **Dimensions as types:** `dims::Dim<M, L, T, I, Θ, N, J, A>` holds the exponents as
  type-level integers (`typenum`). Multiplying and dividing add and subtract exponents, and
  `Pow` multiplies them, so the compiler computes each result's dimension. A named dimension
  is a type alias. `Length / Time` *is* `Velocity`, and another crate's `Speed` is the same
  type, so composition works across crates. (A first design generated operator impls per
  named dimension; the orphan rule would have stopped user crates relating annoray's own
  dimension types.)
- **`dimension!`** declares aliases: `pub Jerk = Length / Time^3;`, `pub Snap = Jerk /
  Time;`, `pub Momentum = Mass * Velocity;`. Powers run from -9 to 9.
- **`dims`** provides the base quantities and common derived ones (area, volume, velocity,
  acceleration, force, momentum, energy, power, pressure, density, charge, voltage,
  resistance, frequency, angular velocity, concentration), declared with the same macro.
- **`Quantity<D>`** is an `f64` with a runtime `Unit`.
  - The unit's dimension is checked against `D` once, at construction. After that, `*`/`/`
    are typed by the compiler. Adding different dimensions is a compile error, with a custom
    `#[diagnostic::on_unimplemented]` message ("quantities of different dimensions do not
    add or subtract"); there is a trybuild test.
  - Units stay values, as for arrays: `km + m` (strict scales) and absolute temperatures
    are runtime `UnitError`s, so the operators return `Result`. They work on owned and
    borrowed operands.
  - Also: `to`, `cast::<D>()`, `dynamic()`, `powi`/`root` (dimension checked at run time),
    `as_number`, comparisons with conversion, and `Display` (`{:.2}` formats the number).
- **`Quantity<Dyn>`** (the default) checks dimensions at run time, for units only known then
  (files). Typed×dynamic products are dynamic, and `cast` brings them back.
- **Python** `annoray.Quantity` wraps `Quantity<Dyn>`: one implementation. Quantities are
  `sel` labels in Rust too (`From<Quantity<K>> for Label`).
- **Examples:** `annoray/examples/quantities.rs` (typed) and its Python twin (runtime) print
  the same lines.
- The scale-mismatch message no longer names Rust API ("convert one first"), so both
  languages report it alike.

**Python counterpart (`annoray.dims`).** Python cannot check before running, so dimensions
are explicit and checked at run time, mirroring the Rust names.
- **`annoray.Dimension`** wraps the Rust `Dimension`:
  `Dimension(length=1, time=-1)`, with `*`, `/`, `**`, `exponents` and `dimensionless`.
  `Unit`, `Quantity` and `DataArray` have `.dimension`.
- **Named dimensions** (`annoray.dims.Length`, `Velocity`, …, the same set as Rust's `dims`)
  are classes with a metaclass:
  - `Length(2.5, "km")` makes a quantity whose unit must be a length.
  - `isinstance(q, Velocity)` asks whether a `Quantity` or `DataArray` has that dimension,
    however it was computed.
  - `Velocity.check(q)` is Rust's `cast`.
  - Named dimensions compose (`Length / Time**3`); `annoray.dimension("Jerk", ...)` names a
    composition, and names with the same exponents interchange.
- **Typed for Pylance/pyright:**
  - Named dimensions are real classes (`class Jerk(Dim, dimension=Length / Time**3)`),
    because checkers reject classes made at run time in annotations. `annoray.dimension()`
    remains the run-time spelling.
  - Annotations read `Quantity[Length]` / `DataArray[Velocity]`, Rust's `Quantity<Length>`.
    The type stub (`_annoray.pyi`, with `py.typed`) makes them generic, and the classes
    accept subscripting at run time (`__class_getitem__`).
  - `Length(...)` returns `Quantity[Length]`, so pyright flags passing a directly built
    `Quantity[Time]` where `Quantity[Length]` is expected. Arithmetic results are
    `Quantity[Any]`, since Python's type system cannot compute dimensions.
- **`@annoray.dims.checked`** enforces those annotations (also bare `Length` and
  `Annotated[Quantity, Length]`) at each call. It resolves string annotations in the
  defining scope too.
- **Ruff and pyright** are configured in `annoray-python/pyproject.toml` and run in CI
  (`ruff check`, `ruff format --check`, `pyright`).
- The Python `quantities` example uses all of this and still prints exactly what the typed
  Rust twin prints.

### Interop with typed unit libraries (features `uom`, `whippyunits`)

A shared bridge trait in `annoray-units`, implemented by each feature:

```rust
/// A unit known at compile time.
pub trait StaticUnit {
    type Value: Element;
    /// What our runtime unit system calls this type's unit.
    fn unit() -> Unit;
    fn from_raw(v: Self::Value) -> Self;   // v is already expressed in unit()
    fn into_raw(self) -> Self::Value;
}
```

Generic API on `DataArrayBase` (and on scalar values used in `sel`):

```rust
da.to_typed::<Q: StaticUnit>() -> Result<ArrayD<Q>>       // checks dimensions, rescales, copies
da.view_typed::<Q>() -> Result<ArrayViewD<Q>>             // zero-copy; only when units match exactly
                                                          // and Q is #[repr(transparent)] over its value
DataArray::from_typed(arr: ArrayD<Q>, dims) -> DataArray  // unit = Q::unit()
ds.sel(("height", Q::new(...)))                            // query converted into the coord's unit
```

| | `uom` | `whippyunits` |
|---|---|---|
| Model | typenum dimensions, values **always stored in SI base units** | Dimensions and prime-factored scales at type level, values stored **in the declared unit** |
| `StaticUnit::unit()` | Read `D::L`, `D::M`, … with typenum's `to_i8()`. Scale is always 1, i.e. SI coherent | Read dimension and scale exponents from the type parameters. They match our `Dimension` and `Scale` one to one |
| Conversion cost | Rescales unless the variable is already in coherent SI | **Free** when the scales match. Otherwise an exact rescale |
| Zero-copy view | Only for coherent-SI variables, and only if `Quantity` turns out to be `repr(transparent)` (to verify; otherwise copy) | Likely, since the scale is in the type (verify the repr) |
| Angle | uom treats angle as dimensionless with a `Kind` marker. Our angle exponent is dropped (rescaled from degrees to rad) on the way into uom | Angle is a real dimension on both sides |
| Affine | `ThermodynamicTemperature` ↔ our K. `degC` data is converted, with the offset applied | Map onto whippyunits' affine units |
| Brand | n/a | whippyunits brand ↔ our optional `brand` |

- Integration tests for each feature: round-trip `DataArray`, typed array, `DataArray` and get the same
  values, unit and label (or the canonical form).
- `cargo hack --feature-powerset` in CI runs `{}, {uom}, {whippyunits}, {uom, whippyunits}`.
- Unit-system details that can't be represented (uom `Kind`s, whippyunits brands we don't track) give
  conversion errors, never silent losses.

## 4. I/O

### Backend abstraction (`annoray-io`)
```rust
pub trait Backend {
    fn open(&self, src: &Source, opts: &OpenOptions) -> Result<RawStore>;     // lazy, CF-undecoded
    fn write(&self, store: &RawStoreView, dst: &Path, opts: &WriteOptions) -> Result<()>;
}
pub trait BackendArray: Send + Sync {
    fn dtype(&self) -> DType; fn shape(&self) -> &[usize]; fn chunks(&self) -> Option<&[usize]>;
    fn read(&self, sel: &Hyperslab) -> Result<TypedArray<Owned>>;
}
```
The pipeline is `open_dataset` = backend.open, then `annoray-cf` decode, then `Dataset`; writing runs the same steps in reverse.
`RawStore` is the plain netCDF data model (groups, dims, vars, attrs) with no CF interpretation.

### Phase A: C bindings (`annoray-io-c`, feature `c-backend`)
- netCDF via the georust `netcdf` crate, and plain HDF5 via `hdf5-metno`. Use the `static` features so
  that CI doesn't depend on system libraries.
- Purpose: get `annoray-core`, `annoray-cf` and units working end to end on real files straight away.
- Later this becomes a **differential-testing oracle**: write with ours, read with C (and the reverse),
  and compare.

### Phase B: pure Rust
- **annoray-netcdf3:**
  - CDF-1, CDF-2 and CDF-5 headers, fixed and record variables, padding and fill values.
  - About 1.5k lines of code.
  - Done first, since it de-risks the shape of the backend trait.
- **annoray-hdf5,** built in layers:
  1. Superblock v0–v3, object headers v1/v2, link messages, compact, dense and symbol-table groups.
  2. Datatypes: fixed-point, float, fixed and variable-length strings, compound, enum, references. Dataspaces.
  3. Layouts: contiguous and compact. Chunked with B-tree v1, plus the newer indexes
     (single-chunk, implicit, fixed array, extensible array, B-tree v2).
  4. Global and fractal heaps, needed for variable-length data and dense attributes.
  5. Filters: deflate (`miniz_oxide`), shuffle, fletcher32, scale-offset (read only). A filter registry
     with a plugin trait.
  6. Writer: we choose a small set of layouts to emit (superblock v2, v2 object headers, chunked with
     B-tree v1 for netCDF-C compatibility, dense attributes when needed), and track free space.
- **annoray-netcdf4:**
  - Maps HDF5 to the netCDF data model: `DIMENSION_LIST`, `REFERENCE_LIST`, `CLASS=DIMENSION_SCALE`,
    `NAME`, `_Netcdf4Dimid`, `_Netcdf4Coordinates`, `_NCProperties`, creation-order tracking,
    phony dims for plain HDF5 files, unlimited dims, groups and user-defined types.
  - Reference documents: the netCDF-4 format spec and the HDF5 File Format Specification v3.

### Implementation notes (M3, as built)
- **The C backend is the `netcdf-c` cargo feature** (`annoray-io-c`, default off). The `netcdf` crate's
  `static` feature builds netCDF-C 4.9 and HDF5 from source, which takes about 1.5 minutes and
  needs cmake. CI's MSRV job skips that crate, since it builds C libraries. Writing `NC_CHAR` needs one `unsafe impl` (a `repr(transparent)` byte), allowed
  locally with a SAFETY comment.
- **Plain HDF5 files are not supported through the C backend.** The `hdf5-metno` bindings were
  skipped: pure-Rust `annoray-hdf5` (M5) covers plain HDF5, tested against h5py-written fixtures.
- **Reads were eager here;** lazy, sliced reads came in M7.
- **`Encoding`** on each `Variable`, and `DatasetEncoding` (unlimited dims) on `Dataset`, record how
  data was stored, as xarray's `.encoding` does. Encoding falls back to xarray's defaults when unset:
  - times use the coarsest exact unit, the first date as reference, and int64;
  - floats get `_FillValue = NaN`;
  - classic files get `string{N}` char dimensions plus `_Encoding = "utf-8"`.
- **We go beyond xarray in netCDF-3:** unsigned integers are stored signed with
  `_Unsigned = "true"` (xarray refuses them), and int64 is narrowed to int32 when the values fit.
- **Known gaps:**
  - No NaT: time variables with missing values stay numeric, with a warning.
  - `TimeDelta` data is written as integers with time units and reads back as a unit-carrying
    quantity, by design.
  - The netCDF crate has no deflate getter, so a file's compression level isn't read back.
- **Verified against Python:** `fixtures/gen_netcdf.py` writes golden files with xarray and
  netCDF4. The tests decode them identically, round-trip every format, and check (in CI) that
  Python xarray reads our output identically too.

### Implementation notes (M4, as built)
- **`annoray-netcdf3` reads and writes CDF-1, CDF-2 and CDF-5 in pure Rust.**
  - Its output is **byte-for-byte identical to netCDF-C's**, padding included (netCDF-C pads with
    the variable's fill value), across all three versions, with one or several record variables.
  - Each library reads the other's files identically, and it reads xarray-written netCDF-3 files.
  - This byte-level test replaces the planned `ncdump` comparison, since `ncdump` isn't built.
- **Robustness:**
  - Every truncation point of every format, 2,000 random byte corruptions, and random headers
    all return errors, never panics.
  - Allocations are bounded by the file size.
  - Streaming files (`numrecs = -1`) are supported.
- **`AutoBackend` in the facade picks the reader from the magic bytes:** netCDF-3 always uses pure
  Rust, and netCDF-4/HDF5 uses the C libraries when the `netcdf-c` feature is enabled, otherwise
  failing with a clear error. So `open_dataset` / `to_netcdf` work for netCDF-3 with no C at all.
  Without the C feature, `to_netcdf` defaults to netCDF-3 (64-bit offsets).

### Implementation notes (M5, as built)
- **The `annoray-hdf5` reader handles everything HDF5 2.0 writes:**
  - superblock v0–v3 and object headers v1/v2 with continuation blocks;
  - symbol-table, compact and dense groups (fractal heap plus v2 B-tree), in creation order
    when the file tracks it;
  - compact and dense attributes;
  - compact, contiguous and chunked layouts with every chunk index (v1 B-tree, single,
    implicit, fixed array including paged, extensible array including super blocks, v2 B-tree);
  - layout message **version 5**, which is new in HDF5 2.0 and same as v4 except filtered chunk
    sizes are as wide as "size of lengths" (established from HDF5's `H5Olayout.c` and
    `H5D*array.c`);
  - deflate, shuffle and Fletcher-32 (verified, accepting either byte order like the library);
  - integers, floats, fixed and variable-length strings, enums, committed datatypes.
  - Compound, reference, opaque and array data are reported as unsupported, not misread.
- **Verified:**
  - Every h5py fixture (`fixtures/gen_hdf5.py`) dumps identically to h5py: earliest, v1.8
    and latest library versions, both byte orders, plus dense creation-ordered groups.
  - netCDF-C's own netCDF-4 files read identically to netCDF-C.
  - Random corruption never panics. `File::with_load_limit` caps decoded dataset size, because a
    corrupt header can claim huge chunked extents (the default is 16 GiB).
- **The writer works in two passes:** every block (heap collections, data, chunks, B-tree nodes,
  object headers) is laid out with address placeholders, then patched and checksummed (lookup3,
  verified against HDF5's stored checksums). This allows references in any direction, which
  netCDF-4 dimension scales need, and one shared global heap.
- **What the writer emits:**
  - superblock v2, and v2 object headers with link and attribute creation order tracked;
  - compact links and attributes (attributes up to 64 KiB, since dense storage isn't written);
  - contiguous, or chunked with a v1 B-tree whose nodes are padded to the full 2K = 64 entries,
    as the library expects;
  - deflate and shuffle;
  - variable-length strings;
  - object references, reference lists and `{dataset, dimension}` pairs.
- **Readers of our output:** our reader, netCDF-C (the HDF5 C library) and h5py all read it
  identically, with h5py resolving every reference to the right object.
- **Facade:** netCDF-4 files still go through the C backend. The pure-Rust path takes over in M6,
  once netCDF-4 semantics (dimension scales, `_Netcdf4Dimid`, …) are on top of `annoray-hdf5`.

### Implementation notes (M6, as built)
- **`annoray-netcdf4` uses netCDF-C's conventions, checked against its files with our HDF5 inspector**
  (`cargo run -p annoray-hdf5 --example inspect -- FILE`):
  - **Dimension scales:** `CLASS="DIMENSION_SCALE"` and `NAME` are NUL-terminated fixed
    strings. Dimension-only scales are empty big-endian `float32` datasets named
    `"This is a netCDF dimension but not a netCDF variable.%10d"`.
  - **Bookkeeping attributes:** `_Netcdf4Dimid` (scalar int), `_Netcdf4Coordinates` (dimension
    ids, on every variable with dimensions), `DIMENSION_LIST` (reference lists) and
    `REFERENCE_LIST` (`{dataset, dimension}` pairs). A variable that clashes with a dimension
    name is stored as `_nc4_non_coord_<name>`.
  - **Root attributes:** `_NCProperties` (we write `version=2,annoray=<version>`), plus
    `_nc3_strict` for the classic model.
  - **`_FillValue`** is both the dataset fill property and an attribute.
  - **Default chunking** is netCDF-C's `nc4_find_default_chunksizes2`, ported exactly (f32
    arithmetic, 4 KiB 1-D unlimited rule, overhang spreading). Unspecified chunking therefore
    matches netCDF-C's output.
- **Attribute order:** compact attributes are ordered by each message's creation-order field.
  This was a real bug: before the fix, attributes came back in header-message order.
- **Verified against netCDF-C:**
  - Reading netCDF-C's and xarray's files gives exactly what netCDF-C reports: dimension order
    and ids, unlimited flags, variable and attribute order, chunk shapes, char arrays, groups.
  - netCDF-C reads our files exactly as it reads its own, in both the full and classic models.
  - Python xarray reads our netCDF-4 output identically (CI).
- **The facade is now pure Rust.** `AutoBackend` picks by magic bytes: netCDF-3 goes to
  `annoray-netcdf3`, netCDF-4/HDF5 to `annoray-netcdf4`. Writing netCDF-4 is pure Rust too. The
  `netcdf-c` feature is now only an alternative backend (`io::c_backend()`) and the
  differential-test oracle.

### Memory-mapped I/O (added during M6, by request)
- **`annoray_io::map_file`** memory-maps files for reading, using `memmap2` with the one `unsafe`
  call, documented. `read_file` is the copying alternative, for files that might be modified
  while open.
- **The HDF5, netCDF-4 and netCDF-3 readers all map by default.** Opening touches only metadata
  pages. Contiguous HDF5 data decodes straight from the map, with no intermediate copy.
- **Hyperslab reads:** `annoray_hdf5::Dataset::read_slice` and `annoray_netcdf3::Netcdf3File::read_slice`
  touch only the chunks, records and rows a slice spans. Property tests check them against full
  reads for every layout, chunk index, record layout and format version.
- **Lazy since M7** (see below).

### Implementation notes (M7, lazy loading, as built)
- **`annoray_core::LazySource`** (`dtype`, `shape`, `read_slice(start, count)`) is what a backend
  provides for each variable. **`LazyArray`** pairs a source with a per-axis selection (an index,
  or `start`/`step`/`len`). `isel` composes selections and reads nothing. The first access reads
  the covering box once, applies the steps, drops the indexed axes, and caches the result in an
  `Arc<OnceLock>`.
- **A `Variable`'s data is either loaded or lazy.** Views, `to_owned` and `isel` keep it lazy.
  `data()`, `typed()`, arithmetic and lookups load it. `data_mut` on lazy data is
  `CoreError::NotLoaded`, so call `Variable::load` or `Dataset::load` first. Display never
  reads: it shows `[N values with dtype=X]`.
- **`annoray_io::RawData`** is `Loaded | Lazy`. `Backend::read_lazy` defaults to `read`. netCDF-3
  (`Nc3Source` over an `Arc<Netcdf3File>`) and netCDF-4/HDF5 (`H5Source` over
  `annoray_hdf5::Dataset::read_slice`) implement it. Unreadable HDF5 types fall back to an eager read,
  so they are still reported as skipped.
- **CF decoding is split into a plan and its application.** The plan (chars, `_Unsigned`, bool,
  mask/scale, times) comes from attributes and dtype alone. Lazy variables wrap their source in a
  `CfSource` that applies the plan to each slice; character slices always span the string axis.
  Decoded times have a fixed type: chrono for real-world calendars, `CfDate` otherwise.
  Out-of-range dates are read-time errors for lazy data, but undecoded-with-a-warning for eager
  data. (NaT is supported since M8.)
- **`open_dataset` is lazy by default** (`OpenOptions::lazy(false)` turns it off). Dimension
  coordinates are always read eagerly, because label selection needs them, as in xarray.
  `tests/lazy_open.rs` checks that lazy and eager opens agree on every fixture, whole and after
  selections.

### Implementation notes (M7, operations, as built)
- **Reductions** (`reduce.rs`): `sum prod mean median std var min max count argmin argmax any
  all` on `Variable`, `DataArray` and `Dataset`. Dimensions are given as `..`, a name, or a
  list. `ReduceOptions` holds `skipna` (default on), `ddof`, `min_count` and `keep_attrs`.
  - Semantics follow numpy's `nan*` functions.
  - Integer sums are exact: checked, and returned as `i64`/`u64`. `f32` stays `f32`.
  - Dates support min, max, mean and median; durations also support sum. Time means are
    rounded to the nearest nanosecond, as xarray does.
  - Units: `var` squares the unit, `std` of °C becomes a kelvin-sized step, summing °C is an
    error, and `count`/`arg*` drop the unit.
  - Datasets drop non-numeric variables for numeric reductions (`numeric_only`).
  - Tested against 378 xarray cases (`fixtures/gen_reductions.py`). Deliberate differences:
    the median of dates is supported, and `any`/`all` of times are not.
- **Alignment** (`align.rs`): `align` and `align_datasets` with the `Inner`, `Outer`, `Left`,
  `Right` and `Exact` joins.
  - Ordering follows pandas: an inner join keeps the left order, an outer join sorts.
  - Missing labels become NaN, and integers are promoted to `f64`. Strings, booleans and dates
    have no NaN, so filling them is an error.
  - Objects that are already aligned are not copied, so lazy data stays unread.
  - Arithmetic now aligns with an inner join, as xarray does; it used to require equal labels.
  - Tested against 76 xarray cases (`fixtures/gen_align.py`).
- **concat / merge** (`combine.rs`): `concat`, `concat_datasets` and `merge`.
  - The defaults are xarray's *new* combine defaults: `join="exact"`, `compat="override"`,
    data variables concatenated only along a new dimension or when they have it, coordinates
    "minimal".
  - `ConcatOptions::legacy()` and `MergeOptions::legacy()` give today's outer-join /
    `equals` / `no_conflicts` behaviour.
  - Compatible units are converted to the first object's unit. Mixed numeric types become
    `f64`.
  - Tested under both default sets against xarray (`fixtures/gen_combine.py`).
- **Parallel chunk reads**: with the `rayon` feature (on by default in the facade), filtered
  HDF5 chunks are decompressed in parallel, in batches that bound memory.
  - Building fill buffers with `Vec::repeat` (zeros come from the allocator) removed most of
    the serial time.
  - A 4000×4000 gzip+shuffle `f64` dataset (128 MB, 256 chunks) now reads in ~50 ms on 8
    cores, against ~335 ms before.

### Implementation notes (M8, missing times, as built)
- **NaT is a reserved value** of each time type, as in numpy: `NaiveDateTime::MIN`,
  `TimeDelta::MIN`, and `CfDate::NAT` (whose year is reserved, so `from_ymd` rejects it). The
  `annoray_core::NaT` trait gives `NAT` and `is_nat()`. Display prints `NaT`.
- **Semantics:**
  - Reductions skip NaT like NaN. An all-NaT mean is NaT, and an all-NaT sum of durations is 0.
  - Arithmetic with NaT gives NaT.
  - Alignment fills missing labels in time data with NaT, which used to be an error.
  - Index keys tolerate NaT.
- **Reading:**
  - NaN, `i64::MIN` (xarray's marker) and `_FillValue`/`missing_value` all decode to NaT.
  - Integer times are masked exactly, inside the time step. They used to be masked through
    f64, which rounded nanosecond timestamps.
  - Durations marked `dtype = "timedelta64[…]"` now decode to `TimeDelta`; they used to
    decode as numbers with a time unit.
  - Lazy and eager decoding agree. The old "NaT not supported" warning and read error are gone.
- **Writing:**
  - NaT is written as `i64::MIN`, without a `_FillValue`, as xarray does.
  - Formats without int64 (netCDF-3) switch to float64 with NaN when NaT is present, as
    xarray does.
  - Durations get `dtype = "timedelta64[ns]"`.
- **Deliberate differences from xarray:**
  - Reductions skip NaT for every operation; xarray's `min`/`max` of dates don't by default.
  - A masked integer time in a non-standard calendar decodes to NaT; xarray raises an
    `OverflowError` in cftime.
  - Exact int64 nanosecond times are written correctly; xarray's encoder wrote such values as
    all fill.
- **Tests:** `tests/nat.rs` reads `fixtures/nc/nat.nc` (generated by `fixtures/gen_nat.py`),
  lazily and eagerly. It also checks reductions, arithmetic and alignment, round-trips in both
  formats, and confirms that Python xarray reads our output (ignored test, run in CI).

### Implementation notes (M8, groupby, as built)
- **`VariableBase::dt(component)`** is xarray's `.dt` accessor. Components: year, month, day,
  hour, minute, second, dayofyear, dayofweek, season. It works for chrono and CF-calendar dates.
  NaT gives NaN (and an empty season).
- **`groupby(group)`** on `DataArray` and `Dataset`. The group can be:
  - a 1-D coordinate;
  - for datasets, a data variable;
  - a date component, as in `"time.month"`.

  **`groupby_bins(group, edges, BinOptions)`** groups by bins instead. `right` and
  `include_lowest` are supported, and labels look like `"(a, b]"`.
- Labels are sorted, as with pandas' factorize. Missing labels (NaN, NaT) belong to no group.
  Every bin is kept, and empty bins reduce to NaN.
- **Operations:**
  - `reduce` and the shortcuts (`sum`, `mean`, … `all`);
  - `first` and `last`;
  - `map`: results that keep the grouped dimension are restored to the original order;
    others are stacked along the group dimension;
  - group arithmetic `gb.binary(op, other)`, also available as `&gb - &clim`, against an
    array indexed by the labels. It adds the grouping variable as a coordinate, as xarray does.
- **Implementation:** one internal `Grouper` (labels plus positions) and one combine step,
  shared by data arrays and datasets through a crate-private `GroupOut` trait. Splitting uses
  `take`, combining uses `concat`, and empty bins are reindexed with `align`.
- **Deliberate differences from xarray:**
  - Dataset variables without the grouped dimension are kept as they are; xarray repeats them
    once per group.
  - The `include_lowest` first bin is labelled `[a, b]`; pandas shows a widened `(a-ε, b]`.
- **Tests:** 17 xarray cases (`fixtures/gen_groupby.py`), covering labels, NaN labels, bins,
  months, seasons, years on 2-D data, noleap dates, `first`/`last`, `map` and anomalies. Also
  tested: NaT labels, datasets, errors and the `.dt` accessor.

### Implementation notes (M8, resample, as built)
- **`resample(dim, freq)`** on `DataArray` and `Dataset` returns the groupby types, with the
  resampled dimension as the group dimension. Everything groupby offers works on the result:
  reductions, `first`/`last`, `map` and group arithmetic.
- **Frequencies** use pandas strings, with multiples:
  - fixed steps: `ns us ms s min h D`, plus the old aliases `N U L S T H`;
  - start-anchored: `MS`, `QS[-MON]`, `YS[-MON]`/`AS`;
  - end-anchored: `W[-DAY]`, `ME`/`M`, `QE[-MON]`/`Q`, `YE[-MON]`/`Y`/`A`.
- **Bins follow pandas:**
  - Fixed steps are closed on the left, labelled with the start, and counted from midnight of
    the first day (`origin = "start_day"`).
  - Start-anchored periods are closed on the left and labelled with the start.
  - End-anchored periods go by calendar date, so the whole last day is in the bin, and are
    labelled with that day.
  - Multiples count from the first period with data. Every bin between the first and last time
    is kept.
- **Calendars:** chrono dates are binned through `CfDate` in the proleptic Gregorian calendar,
  and CF dates in their own calendar. Weeks need a real-world calendar.
- **Deliberate differences from xarray:**
  - Empty groups (resample bins and `groupby_bins`) reduce like empty arrays: sum 0, count 0,
    NaN mean. xarray gives NaN for all three; pandas gives 0 for the sum.
  - Times need not be sorted and may contain NaT, which belongs to no bin. xarray requires a
    monotonic index.
- **Bug fixed along the way:** empty float sums gave `-0.0`, because Rust's float `Sum` starts
  at -0.0. They now fold from +0.0.
- **Tests:** 22 xarray cases (`fixtures/gen_resample.py`) cover the frequency families,
  anchors, multiples and a noleap calendar, checking labels, mean, sum, count and first.
  Separate tests cover NaT, unsorted times, datasets and errors.

### Implementation notes (M8, rolling, as built)
- **`rolling(dim, window, RollingOptions { center, min_periods })`** on `DataArray` and
  `Dataset` supports the reductions sum, prod, mean, median, std, var, min, max, count,
  argmin and argmax, plus `construct(window_dim)`.
- **Semantics follow xarray:**
  - Windows are trailing by default. A centred even window `w` covers `i - w/2 ..= i + w/2 - 1`.
  - `min_periods` defaults to the window size; windows with fewer non-NaN values give NaN,
    `count` included.
  - Integers become `f64`, and `f32` stays `f32`.
  - `argmin`/`argmax` are positions within the window.
  - Units follow the reduction rules. Coordinates are kept.
  - Dataset variables without the dimension, or non-numeric ones, are kept unchanged.
- **Implementation:** the window is built as a NaN-padded trailing dimension, reduced with
  the M7 reductions, then masked by count. Memory scales with the window, so long windows
  over big arrays would want a streaming version later.
- **Tests:** 207 xarray cases (`fixtures/gen_rolling.py`). They cover every reduction for
  NaN floats, int32 and 2-D data, with trailing, centred and even windows and various
  `min_periods`, plus `construct`.

### Implementation notes (M8, missing values, as built)
- **Missing values:**
  - `isnull`/`notnull` on variables and data arrays (NaN, NaT) return booleans.
  - `fillna(f64)` on variables, data arrays and datasets fills floats; other types pass
    through.
- **`where_(cond)` / `where_or(cond, other)`:**
  - `cond` is aligned with an inner join and broadcast over the dimensions it lacks.
  - Integers become `f64` and times get NaT; strings and booleans are an error unless
    `other` is given.
  - `where_or` returns floats, because `other` is an `f64`; xarray keeps the integer type for
    an integer `other`.
- **`dropna(dim, How::{Any, All})`** works on data arrays and datasets. For datasets it looks
  at every data variable with the dimension.
- **`reindex(dim, labels)`** on data arrays and datasets, and `reindex_like(other)`, are built
  on `align` with a right join. Integer data stays integer when nothing is missing.

### Implementation notes (M8, DataTree, as built)
- **`annoray_core::DataTree`** is a node's own `Dataset` plus named children. Its API:
  `add_child`/`with_child`, `get(path)`, `inherited(path)`, `paths()` (depth first),
  `map_over_datasets`, `set_dataset`, `load`, and a `Display` that lists groups.
- **Inheritance** works as in xarray. `inherited(path)` adds the ancestors' dimension (index)
  coordinates the node lacks, ahead of its own; other coordinates stay with the node that
  defines them. (Until M9 every ancestor coordinate was inherited, which differed from
  xarray; the native Python `DataTree` tests caught it.) A child must agree with what it
  inherits: a dimension shared with an inherited dimension coordinate must have the same
  length, and a same-name coordinate must have equal values. Whole subtrees are checked on
  attach.
- **I/O** (facade):
  - `open_datatree`, `open_datatree_with` (lazy by default; `group` picks the root) and
    `open_datatree_with_backend`. Warnings are prefixed with their group path.
  - `DataTree: ToNetcdf` writes each node as a group. Only netCDF-4 has groups, so other
    formats are an error.
- **The default `to_netcdf` format is now netCDF-4** (as in xarray). It had stayed netCDF-3
  without the C feature, a leftover from before the pure-Rust netCDF-4 writer.
- **Tests:** `tests/tree.rs` reads xarray's tree file (`fixtures/gen_tree.py`), checking
  inherited coordinates, nested groups, an empty group and subtrees. It also round-trips the
  tree and checks validation. Python xarray checks every node of our output with
  `assert_identical` (ignored test, run in CI).

### Implementation notes (M8, HDF5 filters, as built)
- **Decoders, all our own except two crates:**
  - bzip2 (307): Huffman, inverse BWT and RLE, with every block's CRC checked.
  - Blosc (32001): format-version-2 frames, multi-block and split streams. Inner codecs are
    our own BloscLZ, plus LZ4 (`lz4_flex`), zlib (`miniz_oxide`) and Zstandard (`ruzstd`).
    Byte and bit shuffles are supported. A version-2 block of a non-multiple-of-8 element
    count is not bit-shuffled at all, as c-blosc does it.
  - Bitshuffle (32008): none, LZ4 or Zstandard. Bits are transposed through an 8×8 matrix in
    a `u64` (10× faster than a bit loop).
  - Scale-offset (6): integers with a fill value, and float D-scaling, computed in the data's
    own type exactly as `H5Zscaleoffset.c` does.
  - N-bit (5): atomic types. Reading it brought support for **bit-field integer types**
    (`Datatype::PackedInt`: a precision and offset inside the word, sign-extended), which HDF5
    files can hold with or without the filter.
  - LZF (32000), LZ4 (32004) and Zstandard (32015). Zstandard and LZ4 sit behind the `zstd`
    and `lz4` features, on by default in the facade; without them, such data is an error
    naming the feature.
- **Encoders (writing):**
  - `Encoding::compression` (and `Storage::compression`) chooses `Compression::{Zstd, Lz4,
    Blosc { codec, level, shuffle }}`, beside deflate and shuffle.
  - Reads report the codec (`Dataset::codec`), so files keep their compression on round-trip.
  - Zstd uses `ruzstd`'s fastest level (its only implemented one). We patch the frame header
    to carry the content size, which the HDF5 zstd plugin needs and `ruzstd` leaves out.
  - Blosc writes one block and stream (LZ4, zlib or Zstandard).
  - bzip2 and BloscLZ stay read-only.
- **MSRV raised to 1.97**, so `ruzstd` 0.9 and `lz4_flex` 0.14 are fine. Clippy's let-chain
  and `is_multiple_of` suggestions were applied across the workspace.
- **Tests:**
  - Small fixture: `fixtures/gen_filters.py` (run with `h5py` + `hdf5plugin`, i.e. HDF5's
    own plugins) writes 34 filtered datasets. Every one must equal HDF5's read, whole and in
    slices.
  - Corruption: 300 randomly corrupted copies of the fixture must never panic (in debug
    builds, where integer overflow also panics).
  - Large chunks: `--big` writes 1024×1024 chunks (~300 MB, not committed; ignored test
    `big_chunks`). These exercise multiple Blosc blocks, Bitshuffle blocks, bzip2 blocks and
    LZ4 blocks.
  - Writing: our Zstd, LZ4 and Blosc files are read back by HDF5's plugins (ignored test,
    run in CI with `hdf5plugin`), and by the facade through netCDF-4.
- **Fixture lesson:** reading a dataset right after writing it can come from HDF5's chunk
  cache, which holds the data before filtering. For lossy filters that is not what a reader
  gets, so the plain copies are now written after reopening the file.

### Implementation notes (M8, interp / open_mfdataset / streaming, as built)
- **`interp(dim, at, InterpMethod::{Linear, Nearest})`** on `DataArray` and `Dataset`, plus
  `interp_like`. It follows numpy's `interp`:
  - Exact hits keep their value, even next to a NaN; `nearest` ties go to the lower
    coordinate. There is no extrapolation: out-of-range targets give NaN.
  - Coordinates may be unsorted or descending, numbers or dates (interpolated in
    nanoseconds).
  - Targets in another unit of the same kind are converted to the coordinate's.
  - Numeric coordinates along the dimension are interpolated; other ones are dropped.
  - Deliberate differences from xarray: a NaN target gives NaN (xarray's `nearest` gives the
    last value), and string coordinates are dropped (xarray back-fills them).
  - Tested against 15 xarray cases (`fixtures/gen_interp.py`).
- **`open_mfdataset(paths, MfOptions { open, combine, concat })`** and **`io::glob`**, which
  uses the `glob` crate.
  - `Combine::ByCoords` (the default) orders the files by the one dimension whose coordinates
    differ; that coordinate may run either way but must be monotonic. It merges if no
    dimension differs. `Combine::Nested(dim)` concatenates in the given order, along an
    existing or a new dimension.
  - The result stays lazy. `concat` of lazy parts builds a `ConcatSource` that reads only the
    files (and parts) a slice covers. Loaded parts join through `MemorySource`, and a
    variable's lazy data is reachable through `as_lazy_source()`.
  - Tested: xarray's own `open_mfdataset` rebuilds the whole from `fixtures/nc/mf` (generated
    by `gen_mf.py`), and so does ours, in any file order.
- **`rolling` reductions work one window at a time**, so memory stays that of the input and
  output; only `construct` materializes windows.
- **Streaming writes.** Lazy datasets (e.g. from `open_mfdataset`) are written without being
  loaded:
  - **CF encoding** of a lazy variable becomes an `EncodeSource` that encodes each slice as it
    is read. Its attributes and stored type come from encoding its first element, and its
    chunk shape is fitted to the real shape. This doesn't apply to strings, durations, times
    without fixed `time_units`, or times in netCDF-3, which are loaded (they are normally
    small).
  - **HDF5:** `WDataset::source` / `WDataset::from_source`, and `write_to(root, sink)` for
    any `Write + Seek`. Chunks and contiguous slabs are read, filtered and written as they are
    produced, at increasing addresses; object headers, B-trees and heaps follow the data, and
    the superblock is written last. `write_file` is the in-memory case. Chunks are now
    assembled by row copies rather than element by element.
  - **netCDF-3:** `write_to` writes in order. Fixed-size variables go in slabs of rows, and
    records in batches, about 32 MB per read.
  - The netCDF-4 and netCDF-3 backends write straight into a buffered file.
  - `tests/streaming.rs` writes a 40 MB synthetic lazy variable, packed to `i16` by CF
    encoding. It checks that netCDF-4 reads exactly one chunk at a time, that netCDF-3 never
    reads it whole, and that the values read back.

### CF layer (`annoray-cf`)
- On decode: apply `_FillValue`, `missing_value`, `scale_factor`, `add_offset` and `_Unsigned`. Parse `units` into `Unit`.
  Turn time variables into `NaiveDateTime` or `CfDate` depending on the calendar (§3 Time), and resolve `coordinates` and `bounds`.
- On encode: the exact inverse, keeping the original dtype, fill value and unit label so the file round-trips byte for byte.
- Integers with fill values are promoted to float + NaN by default, matching xarray. `mask: Masked` keeps the integer dtype and adds a mask instead.

## 5. Indexes and operations
- `Index` trait with `get_loc`, `slice_locs`, `isel` and `equals`, implemented for `SortedIndex<T>`
  (numeric, `CfDateTime`) and `StrIndex`. Selection methods: exact, nearest + tolerance, label slices.
- **Coordinate units:** `sel(lat = 4500.0 km)` style lookups convert the query into the coordinate's
  unit first, and fail if the dimensions don't match.
- Alignment uses inner, outer, left or exact joins. Arithmetic auto-aligns with an inner join and broadcasts by dimension name.
- Later: `concat`, `merge`, `where_`, `groupby`, `resample`, `rolling`, `interp`, `open_mfdataset`,
  `DataTree` (netCDF-4 groups), and `rayon` parallel chunk reads.

### Implementation notes (M2, as built)
- **No separate index objects.** Label lookups run directly on the dimension coordinate (a 1-D
  coordinate named after its dimension). Values map into one of three key spaces: numbers as
  `f64`, strings, and times as `i128` ns. Sorted coordinates use binary search and unsorted ones a
  linear scan. A view's coordinate is already sliced, so lookups can never go stale. Caching for
  repeated `sel` on large coordinates can come in M7 if profiling asks for it.
- **pandas semantics** were checked against xarray 2026.4.0 (`fixtures/xarray_examples.py`):
  - Label slices include both ends.
  - Descending coordinates take `start > stop`.
  - `pad`/`backfill` are positional, so on a descending coordinate `pad` picks the larger
    neighbour.
  - Partial date strings (`"2020-01"`) select the whole period, in any CF calendar.
  - Unsorted coordinates allow exact labels, and slices only between exact labels.
- **Mutable views protect coordinates:** `Repr::Coord` makes a `ViewMut`'s coordinates
  `View`s, so only data variables can be written through a mutable view.
- **Arithmetic:**
  - Broadcasting is by name: the left operand's dims come first, then the right's extras.
  - Shared dimension coordinates had to be equal (`NotAligned`); since M7 operands are aligned with an inner join.
  - Attributes are dropped, as xarray's `keep_attrs=False` default does.
  - A missing unit counts as dimensionless.
  - Integer `+ - *` is checked; `/` is true division.
  - Rust's orphan rules forbid `Result + Result` and `Result * f64`, so those need a `?` first.
- **Fancy indexing** is `take(dim, &[i])` and `sel_take(dim, labels)`. Both return owned data
  because they must copy, so they are methods rather than macro syntax.

## 5a. Indexing macros (`annoray-macros`)

Python-style indexing that never panics. Each macro expands to calls on the `Indexer` /
`LabelIndexer` API below and returns a `Result`, so you finish it with `?`. Anything a macro can do,
plain functions can do too.

### Runtime types (in `annoray-core`, M0)

```rust
pub enum Indexer {                      // positional
    Int(isize),                         // negative counts from the end
    Slice(PySlice),                     // PySlice { start: Option<isize>, stop: Option<isize>, step: Option<isize> }
    Ellipsis,                           // `..` (Python `...`): as many whole axes as needed; positional only
    // Fancy indexing (`[0, 4, 7]`) is deferred to M2: it must copy, so it returns owned data, not a view.
}
pub enum LabelIndexer {                 // label-based (sel)
    Scalar(Label, Method),              // Method::{Exact, Nearest { tolerance: Option<Label> }, Pad, Backfill}
    Slice { start: Option<Label>, stop: Option<Label>, step: Option<isize> },  // inclusive both ends, as in xarray
    List(Vec<Label>, Method),
}
pub enum Label { I64(i64), F64(f64), Str(String), DateTime(NaiveDateTime), CfDate(CfDate), Quantity(f64, Unit) }
// From impls for integers, floats, &str, chrono types, CfDate, and (feature-gated) uom/whippyunits quantities.
impl FromStr for PySlice { … }          // "10:20:2", "::-1", "-5:" → for CLIs / config files
```

**Semantics follow Python exactly:**
- Scalar ints out of range give `Err(IndexError::OutOfBounds { dim, index, len })`.
- Slice bounds **clamp**, as in Python (`x[5:1000]` is fine).
- A step of `0` gives `Err`.
- A negative step reverses (ndarray supports negative strides, so the result is still a view).
- All normalisation uses checked arithmetic.

**Labels and units:** a `Quantity` label is converted into the coordinate's unit before the lookup.
Mismatched dimensions give `Err(UnitError::Incompatible)`. A plain number on a coordinate that has
units is read as already being in the coordinate's unit.

### Macro syntax

```rust
// Positional isel. Dims are taken in the variable's order; `..` fills any remaining dims.
let v = isel!(da[0, 10:20:2, ::-1])?;              // DataArrayView<'_>
let v = isel!(da[-1, ..])?;

// Named isel (preferred). Unnamed dims stay whole.
let v = isel!(ds[time = -1, lat = 10:20, lon = ::2])?;          // DatasetView<'_>
let v = isel!(mut ds[time = 0:12])?;                             // DatasetViewMut<'_>
let v = isel!(da[station = [0, 4, 7]])?;                         // fancy (M2, returns owned)

// Label-based sel. Slices are inclusive. Values are any `impl Into<Label>`.
let v = sel!(ds[time = "2020-01-01":"2020-06-30", lat = 30.0:60.0])?;
let v = sel!(ds[lat = nearest(45.2), lon = nearest(10.0, tol = 0.5)])?;
let v = sel!(da[height = {Quantity::new(2.0, "km")?}])?;        // converted to the coord's unit (e.g. m)
let v = sel!(da[height = {Length::new::<kilometer>(2.0)}])?;    // with the `uom` feature

// Bindings and expressions work as bounds. Wrap anything complex in braces or parens.
let v = isel!(da[time = i:i + n, lat = {cfg.lat_range()}])?;
```

**Parsing rules,** implemented with a `syn` custom parser:
- Each item is `[name =] term`. A term is `expr`, `[expr]? : [expr]? [: [expr]?]`, `..`, `[list]`,
  `nearest(..)`, `pad(..)` or `backfill(..)`.
- Rust lexes `::` as one token, so the parser treats it as two colons. This makes `::2` and `::-1` work.
  The cost is that a path like `a::b` inside a bound must be wrapped (`{a::b}`). A path with no braces
  gives a compile error explaining this, not a wrong parse.
- The output is always mapped to the receiver's reprs: `mut` gives `isel_mut` and a `ViewMut`;
  otherwise you get a `View`. Call `.to_owned()?` for an owned copy.
- Unknown dimension names are runtime errors (`Err(CoreError::NoSuchDim)`), since dims are dynamic.
  Duplicate names in one call are a **compile error**.
- Errors inside the proc macro use `syn::Error::to_compile_error()` and never panic, consistent
  with §2a.

## 8. Risks

| Risk | Mitigation |
|---|---|
| HDF5 format breadth (many versions and index types) | Read everything netCDF-C and h5py emit by default, and write only one well-tested set of layouts |
| netCDF-C accepting the files we write (dimension-scale back-references, creation order) | Differential tests against C from day one. Copy netCDF-C's choices exactly |
| GAT × dtype enum code size and ergonomics | Macro-generated dispatch. Keep the dtype list fixed until M7 |
| Exact scales vs. odd residuals (US survey foot, etc.) | `residual: Ratio<i64>`, falling back to `f64` behind an `Inexact` flag that disables exact equality |
| Strict scale policy feeling painful for exploratory use | `UnitPolicy::AutoRescale`, set per operation or globally |
| chrono only supports proleptic Gregorian (no Julian part of `standard`, no 360_day) | `CfDate` handles those calendars, with explicit fallible conversion to chrono. Never coerce silently |
| uom / whippyunits internals (type parameter layout, `repr`) aren't stable public API | Keep each bridge inside one feature-gated module, pin minor versions, and fall back to copying when zero-copy can't be proven sound |

## 9. Python bindings (M9)

**annoray** for Python (`import annoray`; crate `annoray-python` in `annoray-python/`, PyO3 + maturin;
one wheel per Python version, since rust-numpy does not support abi3) that brings the Rust implementation to Python users, named in the spirit of
xarray. It aims to be **safer** and, where it counts,
**faster** than xarray:
- **Safer:** unit errors fail loudly. The strict defaults hold (exact joins, checked integer
  overflow, no silent NaN-filling), the documented xarray quirks are not copied, and files are
  parsed in memory-safe Rust instead of the netCDF-C/HDF5 C libraries.
- **Faster where it is real:** memory-mapped lazy I/O, parallel decompression, groupby,
  resample and rolling, label lookups and alignment, with the GIL released during work.
  Single elementwise operations are numpy's C loops either way.

**Interoperability is the main constraint:** Python users depend on numpy, pandas, dask and
plotting, so nothing may be a dead end.

Stages:
1. **xarray backend engine.** An `xarray.backends` entry point (`engine="annoray"`) built
   on our lazy readers (a `BackendArray` reading slices), and a writer
   (`annoray.to_netcdf(ds, path)`). Users keep xarray's API and get our I/O: every codec,
   NaT, DataTree groups and `open_mfdataset`. This stage proves out packaging, numpy
   conversion and GIL handling.
2. **Native objects.** `Dataset`, `DataArray` and `Variable` mirror xarray's method names and
   signatures (drop-in where possible), with units through our `Unit` (strings in, pint
   quantities by request). Values are zero-copy numpy views (`.values`), and `to_xarray()` /
   `from_xarray()` convert both ways. Dates map to `datetime64[ns]`; non-standard calendars
   map to cftime objects on conversion. Our stricter defaults are documented differences, not
   different method names.
3. **Differential tests** from Python against xarray, porting a subset of xarray's own tests,
   with the deviation list kept in one place.

4. **Disk-to-disk computation.** Pipelines (open, subset, compute, reduce, write) run on
   data larger than memory. This is chunk-wise evaluation inside the writer and inside
   reductions, not a general task graph. Memory is bounded by threads × chunk (or by the
   streaming budget), never by the size of the data.
   - **Lazy elementwise operations:** arithmetic on lazy data (`a * 2 + b`, `.to()`)
     builds a source that, for any requested box, reads the matching boxes of its operands
     and computes. Alignment, broadcasting and units are settled when the expression is
     built. Writing pulls one chunk at a time, so `(ds.v * 2 + 1).to_netcdf(...)` streams.
     `.values` or `.load()` computes the whole result.
   - **Streaming reductions** of lazy data (sum, mean, var, std, min, max), slab by slab
     along the first dimension within a memory budget (`set_stream_bytes`). Reducing that
     dimension uses the row accumulators (two passes for var/std); keeping it reduces each
     slab on its own. Results equal the in-memory reductions bit for bit. Contiguous groups
     (resample) stream the same way.
   - **`encoding=`** on the native `Dataset.to_netcdf`. It takes xarray's per-variable
     settings; settings not given keep the variable's own (`Dataset::encoding_of_mut`).
   - **Done in the second round:**
     - **Chunk-aligned slabs.** `LazySource::chunking(axis)` reports the on-disk chunk
       grid (size and offset). It is implemented by the HDF5 source, passed through by the
       CF, conversion and map sources, shifted by lazy selections, and agreed across
       concatenated parts. `plan_slabs` ends slabs on chunk boundaries.
     - **Lazy `isnull`/`notnull`/`fillna`** (`MapSource`) **and `where`** (`TypedWhere`,
       reading the condition's part of each box).
     - **Lazy integer-list selection** (`TakeSource`). Runs of consecutive positions are
       read as slices. Many scattered positions are read in windows whose span stays
       within 4× the positions they keep, so far-apart positions don't read what lies
       between them.
     - **Single-pass group reductions** of lazy data (`stream_groups`): each slab is read
       once and its rows go to their group's accumulators, in the in-memory order.
       Reducing group by group had read every chunk once per group, which was 11× slower
       for 12 interleaved groups. Datasets stream their float variables and reduce the
       others group by group.
     - **One streaming budget** (`set_stream_bytes`, default 64 MiB). It covers
       reductions' slabs, the HDF5 reader's decode batch and the writer's compression
       batch (with at least one chunk in flight).
     - **No-panic fix:** `broadcast_to_dims` could panic inside ndarray's `permuted_axes`
       when given inconsistent dimension names. It now returns `DimCountMismatch`, and
       all 11 callers propagate it.
     - **Measured** (ignifly, the same 800 MB variable): copying with a 16 / 64 / 256 MiB
       budget takes 7.0 s / 3.5 s / 3.1 s with +102 / +355 / +415 MB. A groupby over 12
       interleaved groups takes 0.89 s and +270 MB streamed, against 0.83 s and +2.5 GB
       loaded first.
     - **Single-pass streamed variances.** Each slab's exact two-pass moments (count,
       mean, sum of squared deviations) are computed in memory and merged into the running
       ones with the pairwise update of Chan, Golub and LeVeque. Data is read once instead
       of twice. Streamed var/std agree with the in-memory (two-pass) results to rounding
       (within 1e-12 relative for f64 in the tests); sums, means, minima and maxima stay
       bit-identical. `std("t")` on the 800 MB variable went from 1.61 s to 0.86 s, the same
       as `mean`.
   - **Later:**
     - Alignment that has to reindex a lazy operand still loads it.
     - Median and integer reductions of lazy data still load.

   **Implementation notes (done: elementwise, reductions, encoding):**
   - **Lazy elementwise operations:** `BinarySource` and `ConvertSource` (annoray-core
     `ops.rs`).
     - `DataArray::binary` returns a lazy result whenever an operand is lazy, once
       alignment is a no-op. Each operand reads its part of the requested box (dimensions
       it lacks are broadcast) and the box goes through the same `compute` as in memory.
     - The result's dtype comes from computing on empty operands (a 0-d operand reads its
       one value), so building an expression reads nothing.
   - **Streaming reductions** (`reduce.rs`):
     - `streamed` handles lazy f32/f64 data for sum, mean, var, std, min and max. It reads
       slabs along the first axis, sized by `set_stream_bytes` (default 64 MiB).
     - Reducing that axis feeds the slabs to `RowState`, the row accumulators shared with
       the in-memory path, so the order of addition and the result bits are the same.
       Variances merge per-slab moments instead (see the second round below).
     - Keeping that axis reduces each slab on its own.
     - Groupby and resample over contiguous groups reduce lazy views, so they stream too.
   - **HDF5 reads:** the parallel decode batch is capped at 64 MiB of decoded chunks (at
     least one chunk per thread). Before, a large read held threads × 4 chunks.
   - **Measured** (ignifly, an 800 MB variable, deflate-compressed, 10×250×250 chunks,
     16 threads; extra anonymous memory, with the load counted for the in-memory runs):

     | Operation | Streamed | Loaded first |
     |---|---|---|
     | `v * 2 + v[0]` written to disk | 4.1 s, 330 MB | 3.6 s, 3.9 GB |
     | `mean("t")` | 0.86 s, 279 MB | 0.73 s, 1.6 GB |
     | `mean("y")` | 0.85 s, 267 MB | 0.73 s, 1.6 GB |
     | `std("t")` | 1.61 s, 345 MB | 0.73 s, 1.6 GB |

     Streaming memory does not depend on the size of the data.
   - **Tests:**
     - annoray-core `tests/lazy_compute.rs`: a source that records its largest read checks that
       expressions stay lazy, read only the boxes asked for, and match in-memory results
       bit for bit; and that reductions stay within the budget and match bit for bit.
     - pytest: lazy arithmetic, unit conversion and streamed reductions against xarray, and
       `encoding=` round trips.

**annoray stands alone (M9).** annoray is its own library, not a layer over xarray.
xarray is not natively unit-aware, so annoray's objects, units and computation never go
through it.
- `import annoray` loads neither xarray nor pandas, and the only dependency is numpy.
  xarray is the optional extra `annoray[xarray]`, and cftime the extra `annoray[cftime]`
  (dates in non-standard calendars).
- Interop is loaded on use: `engine="annoray"` (the `annoray.backend` entry point),
  `to_xarray`/`from_xarray`, and writing xarray datasets with `annoray.to_netcdf`.
- `annoray.DataTree` is native (core `DataTree`). It offers `open_datatree`,
  `DataTree.from_dict`, `tree[path]`, `paths` (depth first), `children`, `dataset`,
  `to_dataset(path, inherit=True)`, `load`, `to_netcdf` and `to_xarray`/`from_xarray`. Its
  tests found that the core inherited every ancestor coordinate; xarray inherits only
  dimension coordinates, and the core now does too (see M8).
- **Library helpers instead of example helpers:**
  - `to_f64()` on variables and data arrays (numbers and booleans as f64; xarray's
    `.astype(float)`).
  - `DataArray::scalar(v)`.
  - `annoray::date_range(start, periods, freq)` (Python `annoray.date_range`), after
    xarray's `date_range`: fixed steps and period starts; period ends and weeks are not
    supported yet.
- **Examples in pairs:** `annoray/examples/{quickstart,weather,disk_to_disk}.rs` and
  `annoray-python/examples/*.py`, after xarray's quick overview and toy weather data, plus
  the disk-to-disk pipeline. Each pair prints the same text. `tests/test_examples.py`
  checks that, and that the Python examples run with xarray and pandas unimportable. Data
  is generated deterministically (no random numbers), following numpy's evaluation order.
- Unit errors name operands in their order (`incompatible units: m and s`). They had come
  out reversed for addition and subtraction.

**Native `Unit` and `Quantity` (M9).** These replace the Python dataclass `Quantity`, whose
unit was an unchecked string.
- **`annoray.Unit`** wraps the Rust `Unit`. It is parsed and checked when made, multiplies,
  divides and takes integer powers, and compares and hashes exactly (whatever the
  spelling). It also has `is_convertible`, `dimensionless` and `canonical`.
- **`annoray.Quantity`** is a float with a `Unit` (`2.5 * Unit("km")` makes one).
  - Arithmetic follows the array rules: `+`/`-` need the same unit under the strict policy,
    `*`/`/` combine, and `**` takes integer powers.
  - Comparisons convert compatible units; incompatible ones are unequal, and ordering them
    is an error.
  - `.to()`; `float()` only for dimensionless quantities; `f"{q:.2f}"` formats the
    magnitude and appends the unit.
- **Integration:** quantities are data-array operands and `sel` labels;
  `DataArray(..., units=Unit)`, `.to(Unit)`, and `DataArray.unit` (with `.units` as text).
- **Readable derived units** (`annoray-units`): `mul`/`div`/`powi`/`recip`/`root` compose
  the operands' spellings UDUNITS-style (`km s-1`, `km2`, `kg m2 s-3`; `km/min × min` is
  `km`). A composed spelling is kept only if it parses back to exactly the computed unit;
  otherwise the canonical form is shown. Array arithmetic now keeps these spellings (it had
  dropped them).

**Stage 1 implementation notes (done):**
- Rust side (`annoray-python/src/lib.rs`, module `annoray._annoray`): `RawGroup` opens a file with
  `read_lazy` and serves **raw** variables (dims, attributes, storage details, and `read(name,
  start, count)` for one box). `write(...)` builds an annoray `Dataset` from values the
  Python side prepared (numbers, ns-since-epoch datetimes and timedeltas with `i64::MIN` as
  NaT, strings, cftime dates as components) and writes it with our CF encoder. The GIL is
  released for every read and write. `MemorySource` became public for in-memory slices.
- Python side (`annoray-python/python/annoray/`): `backend.py` holds the entry point (`engine="annoray"`,
  `open_dataset`, `open_groups_as_dict`, `open_datatree`, and `guess_can_open` by magic
  number). Raw variables go through xarray's own `StoreBackendEntrypoint`, so xarray's decoder
  runs on top and the results are xarray's own. Arrays support basic indexing: only the
  bounding box is read, and steps and negative steps are applied in numpy. No lock is used,
  since reads are thread-safe, and dask chunks work. `writer.py` holds `annoray.to_netcdf`,
  which takes netCDF4-python encoding names (zlib, complevel, shuffle, chunksizes, dtype,
  packing, fill, time units and calendar, and the compression codecs).
- Tests (`annoray-python/tests/`, 41 tests): reads must be `identical` to `engine="netcdf4"` on every
  fixture, decoded and raw, and under 9 kinds of selection, dask and 8 threads. A variable
  xarray cannot decode (a masked noleap time) must fail the same way. Files written by annoray
  in all five formats must read back identical with netcdf4 and match xarray's own output.
  Packing, time encodings, unlimited dimensions and every codec are covered.
- **Found upstream:** re-opening a file at a second group with `engine="netcdf4"` (after
  `open_datatree`) segfaults inside netCDF4-python (xarray 2026.9). The group test uses
  h5netcdf as its reference.
- **Speed** (200×500×500 float64, zlib level 4 with shuffle, 10×250×250 chunks, Apple
  M-series): full read 0.47 s vs 1.9 s (netcdf4 and h5netcdf), a 100×100 slice 28 ms vs
  97 ms, and writing 2.9 s vs 10 s. The writer now builds and compresses chunks in parallel
  (rayon), in batches bounded to 256 MB, and writes them in order, so files are
  byte-identical to the serial writer.

**Performance work in stage 2.** Measured with `perf` against xarray's tutorial datasets
(`annoray-python/bench/bench_tutorial.py`, Ryzen 7 9700X with 16 threads; every annoray result is
checked against xarray's before it is timed). Causes found and fixed:
- **Rolling:** each window was found with `skip()` on a strided lane, which is O(n²) per
  lane. Windows are now O(1) slices, and lanes run in parallel. 40× slower than xarray became
  about 3× faster.
- **Elementwise arithmetic:**
  - Floats were copied to f64 and mapped through an `Option`. Each operator now has its own
    `Zip` loop, parallel for large arrays.
  - A scalar operand is applied as a constant, with no zero-stride broadcast.
- **Reductions over leading or middle dimensions:** these now accumulate whole rows into the
  result, as numpy does: no transposed copy, and slice loops for contiguous rows. Large
  results are split across threads along a kept dimension. Values are added in lane order, so
  results equal the lane path's bit for bit (tested on three shapes, with and without threads).
  Reductions over trailing dimensions keep lanes, which now run in parallel.
- **Group arithmetic** (`groupby(...) - climatology`): one `take` expands `other` along the
  grouped dimension, then one elementwise operation. Before, each group was copied out and the
  result rebuilt by concatenation.
- **Group reductions:**
  - Contiguous groups (every resample period) are reduced from views.
  - Results are stacked with one copy rather than a checked concatenation. A guard falls back
    to concatenation when parts differ in shape, dtype, unit or coordinates.
- **Unit conversion and CF unpacking:** these ran two passes through an f64 copy using
  `mul_add`, which is a slow library call without FMA enabled at compile time. Each is now one
  parallel pass that computes `x * scale + offset` with numpy's rounding (unpacked values now
  match xarray's bit for bit). f32 data stays f32 under `.to()`.
- **HDF5 shuffle filter:** it wrote bytes with a stride and checked every byte. Writes are now
  sequential, with fixed-width loops for 2-, 4- and 8-byte elements.
- **Benchmark hygiene:** scipy's OpenBLAS threads spin idle and take cores, so the benchmark
  sets `OPENBLAS_NUM_THREADS=1`.

- **Huge pages:** annoray's global allocator is the system allocator, but on Linux it advises
  transparent huge pages (`MADV_HUGEPAGE`) for blocks of 4 MiB or more, as numpy does
  (`annoray-python/src/alloc.rs`, one scoped `unsafe`). Faults on fresh large results fell from one
  per 4 KiB to one per 2 MiB. Libraries do not set a global allocator; Rust programs using
  annoray choose their own.
- **Reusing buffers the core owns:** `binary_reusing_rhs` writes `lhs op rhs` into the right
  operand's buffer when no aligning, broadcasting or unit conversion is needed. It is used
  for group arithmetic (the expanded climatology) and for operands that `binary` has just
  aligned. Python temporaries are not reused: detecting them reliably needs Python 3.14's
  `PyUnstable_Object_IsUniqueReferencedTemporary` and mutable objects.
- **Sums, means, variances and standard deviations along lanes** are streamed rather than
  copied into a buffer. A reduction over all values had been building a 500 MB `Vec`.

Open items:
- `a * 2 + a` on large arrays (0.8×): numpy reuses the temporary from `a * 2`, so it
  allocates and zero-fills once where we do twice. The remaining kernel time is page
  zeroing.
- Annual resample of ersstv5 (0.8×): per-group overhead over 52 small groups.
- Native reads of deflate-compressed files are about 2× slower than netCDF-C; the time is
  in inflate.
