Reading and writing files#

annoray reads and writes netCDF-3, netCDF-4/HDF5 and Zarr with its own pure-Rust code: no netCDF-C, HDF5 or plugin libraries are involved. This chapter covers what is read from netCDF-4 and HDF5 files, how values are encoded on the way back, and how a file is written in place: streamed while its values are produced, appended to, or rewritten a region at a time.

import io
import tempfile
from pathlib import Path

import numpy as np
import annoray as ar

tmp = Path(tempfile.mkdtemp())

Opening#

open_dataset takes a path, the bytes of a file (bytes, bytearray, memoryview) or a binary file-like object, which is read whole from its start, as xarray does. The format is recognised from the contents. Values are read lazily: opening reads the metadata and the dimension coordinates, and other values are read when they are used.

ds = ar.Dataset(
    {"t": (("time", "x"), np.arange(6.0).reshape(3, 2), {"units": "K"})},
    coords={"x": ("x", [10.0, 20.0])},
)
ds.to_netcdf(tmp / "small.nc")
data = (tmp / "small.nc").read_bytes()
print(ar.open_dataset(data)["t"].values)
print(ar.open_dataset(io.BytesIO(data))["t"].units)

[[0. 1.]
 [2. 3.]
 [4. 5.]]
K

Coordinates named by CF attributes#

decode_coords="all" also makes coordinates of the variables that CF attributes such as bounds, grid_mapping, cell_measures and formula_terms name; the attributes move to the variables’ encoding and are written back from there. An attribute that names a variable the file does not have stays an attribute, with a warning (xarray drops it).

cf = ar.Dataset(
    {
        "v": (("x",), np.zeros(3), {"grid_mapping": "crs"}),
        "crs": ((), 0, {"grid_mapping_name": "latitude_longitude"}),
    },
    coords={"x": ("x", [1.0, 2.0, 3.0], {"bounds": "x_bnds"})},
)
cf = cf.assign({"x_bnds": (("x", "nv"), np.zeros((3, 2)))})
cf.to_netcdf(tmp / "cf.nc")
opened = ar.open_dataset(tmp / "cf.nc", decode_coords="all")
print(sorted(opened.coords), opened["v"].encoding["grid_mapping"])

['crs', 'x', 'x_bnds'] crs

Writing over an open file#

Files are opened by mapping them into memory, so a dataset reads from its file for as long as it is open. Writing to a path that already holds a file (with to_netcdf, or NetcdfWriter.create) therefore never truncates it: the new file is written beside it and renamed over it once complete. Datasets opened from the old file keep reading the old data, a dataset can be written back to the file it was opened from, and a failed write leaves the old file as it was. A file reached through a symbolic link is replaced where the link points, and keeps its permissions.

ds = ar.open_dataset(tmp / "small.nc")
ds.assign(t2=ds["t"] * 2.0).to_netcdf(tmp / "small.nc")  # back over its own file
print(list(ds.data_vars), list(ar.open_dataset(tmp / "small.nc").data_vars))

['t'] ['t', 't2']

What is read from netCDF-4 and HDF5#

In the file

In annoray

Complex numbers

complex64/complex128 values, from a compound of two floats named r/i (h5py, netCDF4-python’s nc-complex) or real/imag; written as h5py’s r/i compound. They are read when the file is opened, not lazily (Zarr’s complex arrays are read lazily). netCDF-3 has no complex type.

Compound (record) variables

One variable per field, var.field (nested fields dotted, array members with dimensions of their own); written back as one compound variable when every field is written.

Variable-length (ragged) variables

A CF contiguous ragged array: the values along var_obs, the lengths in var_count; written back as a variable-length variable.

Enumerations

The integer values, with the names in encoding["dtype"].metadata (enum, enum_name), as in xarray; written back as the same type. h5py’s booleans read as booleans.

Virtual datasets

Gathered from their sources (in the same file or others, found relative to it); a missing source file is an error.

Soft and external links

Followed to datasets; links to groups, dangling and cyclic links are skipped with a warning.

Half-precision floats

float32 values with encoding["dtype"] = "float16".

Attributes of any size

Large attributes are kept in dense storage, and written there.

Lossy codecs are decoded bit for bit as their reference libraries decode, built with fused multiply-adds where the reference’s compiler fuses them (clang, and GCC on ARM); builds without them (x86-64) can differ in the last bit of some double values. Writing in place#

NetcdfWriter writes into a netCDF-4 file without rewriting it. NetcdfWriter.create makes a new file from a template: its dimensions, variables, attributes and encodings. The coordinates are written at once; the data variables read as fill values until they are written. A dimension listed in unlimited_dims may start at length 0 and grow.

template = ar.Dataset(
    {"temp": (("time", "x"), np.zeros((0, 4), "f4"), {"units": "K"})},
    coords={
        "time": ("time", np.array([], "datetime64[ns]")),
        "x": ("x", np.arange(4.0)),
    },
)
encoding = {"time": {"units": "hours since 2000-01-01"}, "temp": {"zlib": True}}

Each step’s values are appended as they are produced (append grows every variable along the dimension). dataset() is the file as it now is, opened lazily, so what has been written can be read while writing continues.

with ar.NetcdfWriter.create(
    tmp / "run.nc", template, unlimited_dims=["time"], encoding=encoding
) as w:
    for hour in range(3):
        step = ar.Dataset(
            {"temp": (("time", "x"), np.full((1, 4), 280.0 + hour, "f4"), {"units": "K"})},
            coords={"time": ("time", [np.datetime64("2000-01-01T00") + np.timedelta64(hour, "h")])},
        )
        w.append(step, "time")
    print(w.dataset()["temp"].values[:, 0])

[280. 281. 282.]

Values are encoded with the file’s own encoding of each variable: its packing, fill value, time units and on-disk type. They are converted to the variable’s unit in the file first: values in kelvin go into a variable in degrees Celsius as Celsius. Times that the file’s units cannot hold exactly, in an integer type, are an error, as in xarray.

write puts values into part of the file: along each dimension of region from the given start, along the others from 0. Coordinates along none of the region’s dimensions, such as fixed latitudes, are left as they are.

with ar.NetcdfWriter(tmp / "run.nc") as w:
    fix = ar.Dataset({"temp": (("time", "x"), np.zeros((1, 2), "f4"), {"units": "K"})})
    w.write(fix, region={"time": 1, "x": slice(2, 4)})
print(ar.open_dataset(tmp / "run.nc")["temp"].values)

[[280. 280. 280. 280.]
 [281. 281.   0.   0.]
 [282. 282. 282. 282.]]

to_netcdf(path, mode="a", append_dim=...) and to_netcdf(path, mode="a", region=...) do the same in one call, as xarray’s to_zarr does for Zarr stores.

step = ar.Dataset(
    {"temp": (("time", "x"), np.full((1, 4), 300.0, "f4"), {"units": "K"})},
    coords={"time": ("time", [np.datetime64("2000-01-01T03")])},
)
step.to_netcdf(tmp / "run.nc", mode="a", append_dim="time")
print(ar.open_dataset(tmp / "run.nc").sizes["time"])

4

How the file changes#

Nothing in the file moves. New and rewritten chunks, and the chunk indexes rebuilt to take them, go at the end of the file; the header messages that point to them keep their size and are rewritten where they are, with their checksums. The space a rewritten chunk used before is not reclaimed (h5repack reclaims it). Every value is encoded and checked before anything is written, so values that cannot be stored leave the file as it was. Changes are buffered until flush(), dataset() or close() (or the end of a with block); a writer dropped without closing loses what it buffered.

Files written by netCDF-C, by h5py with its default settings and by annoray can be written in place. Datasets indexed by the structures HDF5 uses with libver="latest" (fixed and extensible arrays, version-2 B-trees) cannot, and are refused with an error. Readers that opened the file before the writer keep seeing it as it was when they opened it: chunks are never overwritten.
